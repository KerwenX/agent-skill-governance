# 一种智能体技能双端协同治理方法

## 一、发明背景与现有技术

随着大模型智能体由固定提示词、固定工具调用逐步演进为基于 Skills 的动态能力扩展模式，Skill 正从简单的自然语言能力描述转变为包含能力定义、触发条件、执行指令、工具调用、资源依赖、权限要求及运行环境约束的可执行能力单元。大量 Skills 被持续创建、发布和更新，并沉淀至共享 Skill Library，由不同用户根据任务需要组合至不同智能体中执行。

在这一模式下，智能体系统面临的问题已经不再局限于“某个 Skill 能否正确完成任务”。即使每一个 Skill 在独立测试中均能够正常运行，当 Skill 数量持续增长、能力边界不断演化、多个 Skills 被动态组合之后，仍可能产生系统级的不确定性和运行风险。

从技术本质上看，该问题可以概括为三个递进层次。

首先是**能力可辨识性问题**。不同 Skills 的能力描述、触发条件或实际能力范围发生交叉，使智能体无法稳定判断用户请求应当由哪个 Skill 处理，进而表现为能力边界重叠、候选 Skill 竞争以及路由结果不稳定。

其次是**调用适用性问题**。多个 Skills 即使在宏观功能上不同，也可能在特定请求、权限状态或任务上下文下同时满足触发条件，导致多个 Skills 被错误共同激活、错误排序或者错误排除。

最后是**组合可执行性问题**。多个 Skills 分别可以独立正确运行，但当它们被组合至同一智能体中时，可能因为前置条件、执行顺序、共享资源、运行状态、工具依赖、权限约束或者输入输出契约不一致而产生组合执行异常。

因此，Skill 生态中的核心治理问题已经由“单个 Skill 是否可用”进一步演化为：

> **多个 Skills 在持续变化和真实组合条件下，其能力关系、调用关系和执行关系是否仍然有效。**

现有 Skill 托管与生命周期管理平台主要关注 Skill 的创建、发布、检索、安装、版本管理和资产复用，其主要管理对象仍然是单个 Skill 本身。该类技术能够记录某一 Skill 发生版本变化，但通常无法进一步确定该变化是否改变了其与其他 Skills 之间的能力边界、路由关系和执行关系，也无法判断修改后的 Skill 是否会影响已经使用相关 Skill 的其他智能体。

另一方面，现有 Skill Retrieval、Routing 和 Compatibility 技术已经开始研究 Skill 相似性、候选选择、能力去重、Skill Pair Compatibility 以及 Skill Relationship Graph 等问题。因此，单纯判断两个 Skills 是否相似、是否冲突或者是否应该共同进入候选集合，已经难以形成足够稳定的技术区别。

现有 Agent Evaluation 和 Skill Evaluation 技术还能够自动生成任务、执行 Agent、记录 Tool Call 和 Execution Trace，并根据执行结果判断 Agent 或 Skill 是否正常。自动 Skill 演进技术进一步可以根据失败结果利用大模型修改 Skill 并重新测试。因此，简单的“检测—LLM 修复—重新测试”同样不足以构成本发明的核心技术方案。

此外，Human-in-the-loop 已经广泛应用于模型训练、Agent 行为纠正和自动化系统治理。因此，本发明所强调的也不是简单地“让开发者或者用户参与决策”，而是需要解决更加具体的技术问题：

> **如何在开发者发布和演进 Skill 时，以及用户实际组合和运行 Skills 时，分别触发具有不同治理作用域的治理过程；如何将潜在 Skill 关系失效转换为可重复执行和验证的技术证据；如何根据关系失效类型确定相应治理约束；如何将机器或人的治理判断编译为可直接约束 Skill 检索、路由、规划和执行的机器规则；以及如何使用户端真实运行产生的新证据继续反向推动开发者端的全局治理。**

基于上述分析，本发明不将 Skill 冲突检测、自动修复或者人工参与作为孤立创新点，而是建立一种面向 Skill 全生命周期的**开发者端—用户端双端协同治理机制**。

## 二、发明总体设计

本发明中的“双端”具有明确且唯一的含义，即：

**开发者端**和**用户端**。

开发者端面向 Skill 的创建、修改、发布和版本演进。其治理目标是判断一个 Skill 的新增或变化是否会破坏共享 Skill Library 中已有的 Skill 关系，以及是否会影响已经使用相关 Skill 的智能体和工作流。因此，开发者端主要形成能够作用于共享 Skill 生态的**全局治理结果**。

用户端面向 Skill 的选择、组合和实际运行。即便所有 Skills 已经通过开发者端发布验证，当用户将多个 Skills 配置至自己的智能体中以后，由于用户权限、任务类型、资源状态、运行环境以及具体上下文不同，仍然可能产生仅在当前用户环境中出现的组合冲突。因此，用户端主要形成具有用户、智能体、会话或者任务作用范围的**局部治理结果**。

两端解决的问题不同，但共同围绕 Skill Relationship 的有效性展开治理。

设共享 Skill 集合为：

$$
\mathcal{S}=\{S_1,S_2,\ldots,S_n\}
$$

系统除了保存各个 Skill 本身，还维护一组与 Skill 关系治理有关的状态：

$$
\mathcal{G}
=
\{
\mathcal{C},
\mathcal{W},
\mathcal{K},
\mathcal{H}
\}
$$

其中，$\mathcal{C}$ 表示 Skill 关系及冲突状态，$\mathcal{W}$ 表示用于复现 Skill 关系失效的 Conflict Witness 集合，$\mathcal{K}$ 表示机器可执行的 Governance Contract 集合，$\mathcal{H}$ 表示历史运行、验证及治理证据。

因此整个 Skill 系统的真实治理状态表示为：

$$
State_t=
(
\mathcal{S}_t,
\mathcal{G}_t
)
$$

当 Skill 被新增、修改、组合或者运行上下文发生变化时，本发明需要判断：

$$
State_t\rightarrow State_{t+1}
$$

之后，原有 Skill Relationship 是否仍然保持有效。

围绕上述目标，本发明建立统一治理过程：

$$
\boxed{
\text{Detect}
\rightarrow
\text{Decide}
\rightarrow
\text{Resolve}
\rightarrow
\text{Verify}
}
$$

Detect 用于识别并动态确认 Skill Relationship 是否失效；Decide 用于确定正确的治理关系；Resolve 用于将治理关系编译为机器可执行约束并实际改变系统运行；Verify 用于验证原关系失效是否已经消除，以及治理行为是否产生新的系统影响。

完成一次 Verify 后，新产生的执行证据继续进入下一轮 Detect，因此形成持续循环：

$$
\text{Detect}
\rightarrow
\text{Decide}
\rightarrow
\text{Resolve}
\rightarrow
\text{Verify}
\rightarrow
\text{Detect}
$$

开发者端与用户端均遵循这一治理范式，但其触发源、分析范围、治理作用域和验证对象不同。

## 三、双端协同治理技术方案

本发明的技术处理链可以统一表示为：

$$
\boxed{
\text{双端技术事件}
\rightarrow
\text{Skill关系识别}
\rightarrow
\text{关系失效证据化}
\rightarrow
\text{治理决策}
\rightarrow
\text{治理契约编译}
\rightarrow
\text{契约合并与执行}
\rightarrow
\text{生命周期控制}
\rightarrow
\text{影响验证}
}
$$

该链条中，每一阶段的输出均构成后一阶段的输入，从而避免冲突检测、人工决策、规则生成和测试验证成为彼此孤立的功能模块。

### 3.1 Skill 执行语义建模与双端技术触发

不同来源的 Skill 可能采用不同描述方式。为了能够统一分析 Skill 之间的能力边界、触发条件以及执行兼容性，本发明首先将 Skill 转换为统一的 Skill Execution Contract。

对于任意 Skill $S_i$，定义：

$$
SC_i=
(
D_i,
T_i,
I_i,
O_i,
P_i,
A_i,
R_i,
E_i,
Dep_i,
Perm_i,
V_i
)
$$

其中，$D_i$ 表示 Skill 能力语义，$T_i$ 表示触发或适用条件，$I_i$ 和 $O_i$ 分别表示输入和输出约束，$P_i$ 表示执行前置条件，$A_i$ 表示 Skill 可以调用的 Tool 或 Action，$R_i$ 表示 Skill 访问或修改的运行资源，$E_i$ 表示 Skill 执行产生的状态变化或者副作用，$Dep_i$ 表示外部依赖，$Perm_i$ 表示权限要求，$V_i$ 表示 Skill 版本。

上述信息可以从 Skill Metadata、Description、Instruction、Script、Tool Schema、Manifest 以及历史 Execution Trace 中综合提取，并不要求 Skill 原生采用完全一致的数据结构。

其目的在于将原本分散在自然语言说明、工具定义和执行代码中的能力与执行约束转换为统一可计算的关系表示，使后续治理不局限于文本相似度，而能够同时处理语义、触发、执行和环境层面的关系。

对于两个 Skills $S_i$ 与 $S_j$，定义其关系状态为：

$$
CR_{ij}
=
(
c_{cap},
c_{trigger},
c_{route},
c_{order},
c_{resource},
c_{state},
c_{dependency},
c_{permission},
c_{io}
)
$$

其中分别表示能力边界、触发、路由、执行顺序、资源、状态、依赖、权限以及输入输出等关系维度。同一 Skill Pair 可以同时存在多个关系维度，例如两个 Skill 既可能在能力范围上重叠，也可能在真实运行过程中访问同一共享资源。

开发者端治理始于 Skill 本体发生变化。

设某一 Skill 当前版本为：

$$
S_i^{(v)}
$$

开发者修改后形成：

$$
S_i^{(v+1)}
$$

系统计算结构化变化：

$$
\Delta S_i
=
S_i^{(v+1)}
-
S_i^{(v)}
$$

进一步表示为：

$$
\Delta S_i
=
(
\Delta D_i,
\Delta T_i,
\Delta P_i,
\Delta A_i,
\Delta R_i,
\Delta E_i,
\Delta Dep_i,
\Delta Perm_i
)
$$

这里的差异不是普通文本 Diff，而是 Skill Contract 层面的执行语义变化。系统根据变化类型确定可能受到影响的 Skill Relationship。例如 Description 或 Trigger 的变化主要影响 Capability Boundary 和 Routing Relationship，而 Dependency、Resource 或 Side Effect 的变化则更可能影响组合执行关系。

因此开发者端的触发过程为：

$$
\Delta S_i
\rightarrow
AffectedRelationshipType
\rightarrow
DeveloperGovernance
$$

用户端治理则始于 Skill 实际使用状态发生变化。

设用户所配置的 Agent 为 $A_u$，当前 Skill Set 为：

$$
\mathcal{S}_u
=
SkillSet(A_u)
$$

当前运行上下文表示为：

$$
X_u
=
(
Task,
Permission,
Resource,
Environment,
Session
)
$$

用户端判断的并不是脱离上下文的：

$$
Conflict(S_i,S_j)
$$

而是：

$$
Conflict(S_i,S_j\mid X_u)
$$

只要当前 Skill Set 或运行上下文发生变化：

$$
\Delta\mathcal{S}_u\neq0
$$

或者：

$$
\Delta X_u\neq0
$$

即可触发用户端治理。

因此两个端的技术触发关系可以统一表示为：

$$
\boxed{
\Delta Skill
\Rightarrow
DeveloperGovernance
}
$$

以及：

$$
\boxed{
\Delta SkillSet
\lor
\Delta Context
\Rightarrow
UserGovernance
}
$$

前者治理 Skill 演化对共享生态产生的全局影响，后者治理真实用户环境中的局部组合关系。

### 3.2 Skill 关系识别、Conflict Witness 生成与动态确认

双端触发后，系统进入 Detect 阶段。

系统首先基于 Skill Contract 建立候选关系，而不是直接对所有 Skill Pair 进行完整动态仿真。

对于目标 Skill $S_i$，定义候选邻域：

$$
\mathcal{N}(S_i)
=
\left\{
S_j
\mid
Rel(S_i,S_j)\geq\tau_r
\right\}
$$

其中：

$$
Rel(S_i,S_j)
=
f(
D,
T,
P,
A,
R,
E,
Dep,
Perm
)
$$

该关系函数综合考虑能力语义、触发条件、前置条件、工具、资源、状态副作用、外部依赖和权限，而不是单一 Description Similarity。

开发者端的主要搜索空间为目标 Skill 与共享 Skill Library 的关系：

$$
S_i\times\mathcal{S}_{library}
$$

用户端的主要搜索空间则为当前实际 Skill Set 内部的关系：

$$
\mathcal{S}_u\times\mathcal{S}_u
$$

并受到用户上下文 $X_u$ 的进一步约束。

静态候选关系只表示：

> 某种 Skill Relationship 具有潜在失效可能。

因此将其记为：

$$
CR_{ij}^{candidate}
$$

而不直接视为真实冲突。

为了判断候选关系究竟如何可能失效，本发明进一步从两个 Skill Contract 中抽取差异维度：

$$
\Delta R_{ij}
=
\Delta(
SC_i,
SC_j
)
$$

并表示为：

$$
\Delta R_{ij}
=
(
\Delta_{cap},
\Delta_{trigger},
\Delta_{pre},
\Delta_{resource},
\Delta_{state},
\Delta_{dependency},
\Delta_{permission},
\Delta_{io}
)
$$

系统根据这些差异首先形成 Relationship Violation Hypothesis：

$$
VH_{ij}
=
Hypothesis(
\Delta R_{ij}
)
$$

该 Hypothesis 用于描述：

> 在何种条件下，原本假设成立的 Skill Relationship 可能发生失效。

例如，若主要差异来源于 Trigger，则 Violation Hypothesis 主要关注两个 Skill 触发边界的交集；若主要差异来源于 Precondition，则 Hypothesis 主要关注不同环境状态和执行先后条件；若主要差异来源于 Resource，则 Hypothesis 重点关注共享资源、并发执行和资源状态变化。

随后系统根据 Violation Hypothesis 构造完整的 Witness Context：

$$
X_W
=
(
Q,
Permission,
ResourceState,
Environment,
SkillSet,
ExecutionCondition
)
$$

其中不仅包含测试请求 $Q$，还包括权限、资源状态、运行环境、参与执行的 Skill Set 和执行条件。

在此基础上定义 Conflict Witness：

$$
W=
(
X_W,
\Pi,
O
)
$$

其中，$\Pi$ 表示 Execution Strategy，$O$ 表示需要观察的行为集合。

Execution Strategy 可以包含：

- 分别执行 $S_i$ 和 $S_j$；
- 同时加载 $S_i$ 与 $S_j$；
- 改变 Skill 执行顺序；
- 改变权限或资源状态；
- 改变 Context；
- 对同一 Witness 重复执行多轮。

Conflict Witness 的目标不是随机寻找一个失败样本，而是最大化候选 Skill Relationship 的行为差异：

$$
W^*
=
\arg\max_W
D_B
\left(
Behavior(S_i,W),
Behavior(S_j,W)
\right)
$$

其中，$D_B$ 可以综合 Skill Route、Skill Load、Tool Call、执行顺序、Resource Access、State Transition 和最终 Output 等行为差异。

系统随后在隔离环境中执行多轮仿真：

$$
T^{(k)}
=
Simulate(
W,
\mathcal{S},
k
)
$$

并采集：

$$
T=
(
Route,
SkillLoad,
ToolCall,
ResourceAccess,
StateTransition,
Output,
Exception
)
$$

为了避免一次随机失败被误判为稳定冲突，本发明进一步计算同一 Witness 下的关系失效率：

$$
ViolationRate(W)
=
\frac{
N_{violation}
}{
N_{simulation}
}
$$

其中 $N_{violation}$ 表示观察到目标关系失效的轮次，$N_{simulation}$ 表示总仿真轮次。

只有当：

$$
ViolationRate(W)\geq\tau_v
$$

并且观察到的行为满足对应 Relationship Violation 的判定条件时，系统才完成：

$$
CR_{ij}^{candidate}
\rightarrow
RV_{ij}^{confirmed}
$$

其中 $RV_{ij}^{confirmed}$ 表示已经由运行证据确认的 Relationship Violation。

如果动态执行无法稳定复现该关系失效，则候选关系被标记为 False Positive，而不进入后续治理。

因此 Detect 阶段的最终输出为：

$$
\boxed{
RelationshipViolation
+
ConflictWitness
+
ExecutionEvidence
}
$$

上述结构化输出直接作为治理决策阶段的输入。

### 3.3 Relationship Violation 到 Governance Decision 的映射

确认 Relationship Violation 后，系统需要回答的不是简单的“是否发生了冲突”，而是：

> **该关系失效后，正确的机器关系应该是什么。**

为了避免后续治理完全依赖 LLM 自由生成修复方案，本发明首先将 Relationship Violation 归一化为结构化描述：

$$
RV=
(
Type,
Condition,
Subjects,
ObservedBehavior,
ExpectedRelation,
Risk
)
$$

其中，Type 表示关系失效类型，Condition 表示产生失效的运行条件，Subjects 表示相关 Skills，ObservedBehavior 表示实际观察到的错误行为，ExpectedRelation 表示系统需要建立的正确关系，Risk 表示治理错误可能产生的技术风险。

系统根据 Relationship Violation 类型和 Expected Relation，将失效关系映射至一个确定的治理动作空间：

$$
RI
=
Map(
Type,
Condition,
ExpectedRelation
)
$$

其中 $RI$ 表示 Resolution Intent。

不同 Relationship Violation 与治理约束之间形成如下对应关系：

| Relationship Violation | 治理意图 | 主要运行约束 |
|---|---|---|
| 多个 Skills 同时被选择，但只应选择一个 | 路由仲裁 | Priority / Exclusion |
| Skill 适用条件过宽 | 收缩能力边界 | Predicate |
| 专用 Skill 与通用 Skill 同时满足条件 | 专用能力优先 | Predicate + Priority + Fallback |
| 多个 Skills 必须按先后关系执行 | 建立执行序列 | Order |
| 一个 Skill 失败后应调用另一个 | 条件替代 | Fallback |
| 多个 Skills 不允许同时访问同一资源 | 运行互斥 | Exclusion / Isolation |
| 多个 Skills 可以共同运行但资源不能共享 | 资源隔离 | Isolation |
| 当前 Skill 缺少必要权限 | 条件阻断或替代 | Permission Guard + Predicate + Fallback |
| 上游输出不满足下游输入 | 接口适配 | Adapter + Order |
| Runtime Dependency 不兼容 | 环境约束 | Version Constraint + Isolation |
| 一个 Skill 的状态变化破坏另一 Skill | 状态保护 | Order / Exclusion / Runtime Guard |

该映射不是简单展示关系，而用于限制后续 Governance Decision 的动作空间。

也就是说，当确认某类关系失效后，系统首先确定：

> 允许采用哪些类型的治理动作。

随后再根据冲突风险、影响范围和系统不确定性确定由机器自动决策，还是触发开发者或用户参与。

定义治理升级评分：

$$
E_s
=
\alpha U
+
\beta R
+
\gamma I
+
\delta V
$$

其中，$U$ 表示系统对正确治理结果的不确定性，$R$ 表示错误治理可能造成的运行风险，$I$ 表示受影响的 Skill、Agent 或用户范围，$V$ 表示治理操作的不可逆程度。

当：

$$
E_s<\tau_e
$$

且存在高置信度 Resolution Intent 时：

$$
Mode=Automatic
$$

系统自动完成治理决策。

当：

$$
E_s\geq\tau_e
$$

时：

$$
Mode=Interactive
$$

系统触发对应端参与。

如果问题来源于 Skill 创建、修改或者发布，则进入 Developer Decision；如果问题来源于用户 Skill 组合和真实运行上下文，则进入 User Decision。

系统提供给开发者或用户的不是完整原始日志，而是由上一阶段自动整理得到的 Conflict Evidence Package：

$$
CEP=
(
ConflictType,
W,
Trace,
Divergence,
Impact,
ResolutionIntent
)
$$

开发者或用户只需针对：

> 正确的 Skill Relationship 应当是什么

进行确认或者调整。

无论治理结果来自系统自动判断、开发者决策还是用户决策，最终均转换为统一治理决策：

$$
RD=
(
Predicate,
Priority,
Exclusion,
Order,
Fallback,
Isolation,
Adapter,
PermissionConstraint
)
$$

因此 Decide 阶段形成了一条明确的数据转换关系：

$$
\boxed{
RelationshipViolation
\rightarrow
ResolutionIntent
\rightarrow
GovernanceDecision
}
$$

### 3.4 Governance Contract 编译与运行控制

Governance Decision 仍然不能直接作为最终治理结果。

如果系统只保存自然语言形式的“Skill A 应优先于 Skill B”或者“Skill C 应先于 Skill D 执行”，这些结论无法稳定作用于不同版本、不同 Agent 和不同上下文。

因此本发明设置 Governance Contract Compiler，将 Governance Decision 编译为机器可执行治理契约：

$$
GC=
(
Subject,
Scope,
Predicate,
Priority,
Exclusion,
Order,
Fallback,
Isolation,
Adapter,
PermissionConstraint,
Version,
Evidence,
Validity,
ConstraintClass
)
$$

其中，Subject 表示受约束的 Skill 或 Skill Set，Scope 表示治理规则的作用范围，Predicate 表示规则生效的上下文条件，Priority 表示多个 Skills 同时满足条件时的优先关系，Exclusion 表示互斥关系，Order 表示执行先后关系，Fallback 表示失败替代关系，Isolation 表示资源隔离关系，Adapter 表示输入输出转换约束，PermissionConstraint 表示权限相关运行约束，Version 表示 Contract 所适用的 Skill 版本，Evidence 指向生成该 Contract 的 Conflict Witness，Validity 表示规则有效条件，ConstraintClass 表示该规则的约束等级。

如果两个 Skills 在上下文 $X$ 下不得同时执行，则表示为：

$$
S_i\perp S_j\mid X
$$

如果多个 Skills 需要满足执行顺序，则表示为：

$$
S_i\prec S_j
$$

如果一个 Skill 失败后需要调用另一个 Skill，则表示为：

$$
S_i\rightarrow S_j
$$

如果上下游之间需要经过适配器 $A_{ij}$，则表示为：

$$
O_i
\xrightarrow{A_{ij}}
I_j
$$

使得：

$$
Schema(A_{ij}(O_i))
\models
I_j
$$

Governance Contract 并非静态报告，而会直接进入 Agent 的真实运行链。

在 Skill Retrieval 阶段：

$$
CandidateSet'
=
Filter(
CandidateSet,
GC
)
$$

系统根据 Predicate、PermissionConstraint 和 Exclusion 过滤不符合当前条件的 Skill。

在 Router 阶段：

$$
Rank'
=
ApplyPriority(
Rank,
GC
)
$$

系统根据 Priority 调整候选 Skill 排序。

在 Planner 阶段：

$$
Plan'
=
ApplyOrder(
Plan,
GC
)
$$

系统根据 Order 和 Adapter 形成正确 Skill Composition。

在 Runtime 阶段：

$$
Execution'
=
Guard(
Execution,
GC
)
$$

系统根据 Exclusion、Isolation、Fallback 和 PermissionConstraint 控制真实执行过程。

因此治理链最终形成：

$$
\boxed{
RelationshipViolation
\rightarrow
GovernanceDecision
\rightarrow
GovernanceContract
\rightarrow
RuntimeBehaviorChange
}
$$

这一转换使治理结果从分析信息真正转化为系统运行状态。

### 3.5 Global Contract 与 Local Contract 的确定性合并

开发者端与用户端产生的 Governance Contract 具有不同作用域。

开发者端形成的 Contract 主要为：

$$
GC_G
$$

其默认作用域为：

$$
Scope(GC_G)=Global
$$

用户端形成的 Contract 主要为：

$$
GC_L
$$

其作用域可以为：

$$
Scope(GC_L)
\in
\{
Tenant,
User,
Agent,
Session,
Task
\}
$$

系统实际运行时不能简单规定“Local 永远覆盖 Global”或者“Global 永远覆盖 Local”，否则一方面会使局部用户需求无法表达，另一方面又可能使 Local Contract 绕过全局安全约束。

因此，本发明进一步定义 Contract Constraint Class：

$$
ConstraintClass
\in
\{
Invariant,
Default,
LocalRefinement
\}
$$

其中，Invariant 表示全局不可被局部放宽的强制约束，例如权限上限、高风险资源互斥、安全隔离等规则；Default 表示共享环境中的默认 Skill Relationship，例如默认 Priority、Routing Predicate 或 Fallback；LocalRefinement 表示用户端针对更窄上下文形成的局部治理规则。

系统首先根据当前上下文 $X$ 和 Skill Version $V$ 判断 Contract 是否适用：

$$
Applicable(GC,X,V)
=
Predicate(GC,X)
\land
VersionMatch(GC,V)
$$

获得当前适用 Contract 集合：

$$
\mathcal{K}_{app}
=
\left\{
GC_i
\mid
Applicable(GC_i,X,V)=1
\right\}
$$

对于不同 Constraint Class，系统采用确定性约束顺序：

$$
Invariant
>
LocalRefinement
>
GlobalDefault
$$

但 LocalRefinement 只有在 Global Contract 允许 Override 时才能改变 Default 行为。

Local Contract 不允许放宽 Global Invariant，即：

$$
Override(
GC_L,
GC_G^{Invariant}
)
=
False
$$

但 Local Contract 可以在更加具体的上下文中覆盖 Global Default，例如：

$$
Scope_{local}
\subset
Scope_{global}
$$

且：

$$
Predicate_{local}
\subset
Predicate_{global}
$$

时，可以在 Local Scope 内使用更具体的 Priority、Fallback 或 Ordering。

同时定义 Scope Specificity：

$$
Task
>
Session
>
Agent
>
User
>
Tenant
>
Global
$$

对于允许 Override 且 Constraint Class 相同的规则，更具体 Scope 的规则具有更高应用优先级。

因此实际生效规则可表示为：

$$
GC_{effective}
=
Resolve(
\mathcal{K}_{app},
ConstraintClass,
ScopeSpecificity
)
$$

该 Resolve 过程首先保证 Invariant 不被违反，然后在 Default 和 LocalRefinement 中按照 Scope Specificity 与 Predicate Specificity 确定最终规则。

如果存在两条同等级、同 Scope、同 Predicate 范围，但执行动作互相矛盾的 Contract，则系统不采用“最后写入优先”等非确定性机制，而将该情况定义为：

$$
ContractMergeConflict
$$

并重新触发：

$$
Detect
\rightarrow
Decide
$$

形成新的治理流程。

因此，Global Contract 与 Local Contract 的关系不是简单覆盖关系，而是一个具有：

- 约束等级；
- 作用域；
- 条件范围；
- 版本；

共同控制的确定性合并机制。

该机制保证：

> 用户端可以针对真实上下文进行局部修正，但不能突破开发者端已经确认的不可放宽全局约束。

---

### 3.6 Governance Contract 生命周期与版本一致性

Governance Contract 并不是生成后永久有效。

由于 Skill 会持续更新，用户上下文会变化，Global Contract 也会不断演进，因此 Contract 本身也需要具有明确生命周期和版本一致性机制。

本发明定义 Contract 状态集合：

$$
State(GC)
\in
\{
Candidate,
Verified,
Active,
Stale,
Revalidating,
Retired,
RolledBack
\}
$$

Governance Contract 初次生成时处于：

$$
Candidate
$$

经过验证后进入：

$$
Verified
$$

正式参与系统运行后进入：

$$
Active
$$

即：

$$
Candidate
\rightarrow
Verified
\rightarrow
Active
$$

同时，为每个 Contract 记录其依赖状态：

$$
Dependency(GC)
=
(
SkillVersion,
ParentContract,
ContextSchema,
ResourceConstraint,
PermissionModel
)
$$

当其中任一依赖发生不兼容变化：

$$
\Delta Dependency(GC)\neq0
$$

则 Contract 不能继续被视为已验证状态，而转换为：

$$
Active
\rightarrow
Stale
$$

Stale 表示：

> Contract 可能仍然正确，但由于其依赖基础发生变化，原有验证结论已经不能被直接复用。

系统随后进入：

$$
Stale
\rightarrow
Revalidating
$$

重新执行该 Contract 对应的 Conflict Witness 和受影响回归案例。

若验证通过：

$$
Revalidating
\rightarrow
Active
$$

若该 Contract 已被新的 Contract 完整替代：

$$
Revalidating
\rightarrow
Retired
$$

若验证失败且必须恢复旧版本运行状态：

$$
Revalidating
\rightarrow
RolledBack
$$

不同类型 Contract 在 Stale 状态下还可以采用不同运行策略。

对于普通 Routing Default，可定义：

$$
StalePolicy
=
FallbackToParent
$$

即暂时回退至上一级 Global Default。

对于仍具有较高可信度但尚未完成重验证的规则，可以采用：

$$
StalePolicy
=
KeepLastVerified
$$

对于权限、安全或高风险资源类 Invariant，则可以采用：

$$
StalePolicy
=
FailClosed
$$

即在重新验证完成之前继续保持更严格约束，而不是因为 Contract Stale 自动放宽限制。

通过上述机制，Governance Contract 不再只是一个静态配置，而成为一个随 Skill Version、用户 Context 和全局治理状态持续演进的受控机器状态。

---

### 3.7 影响分析与回归验证

Governance Contract 生成、合并或者版本状态变化以后，系统需要判断：

> 原有 Relationship Violation 是否已经被消除，以及此次治理是否影响其他已有正确行为。

本发明建立 Skill Impact Graph：

$$
G=(V,E)
$$

其中节点至少包括：

$$
V=
\{
Skill,
Agent,
Workflow,
Tool,
Resource,
GovernanceContract
\}
$$

边用于表示：

- uses；
- invokes；
- depends-on；
- reads；
- writes；
- governed-by。

对于一次 Skill 或 Governance Contract 变化：

$$
\Delta
$$

系统计算：

$$
\mathcal{A}(\Delta)
=
Reachable(
G,
\Delta
)
$$

得到真正受本次变化影响的：

$$
AffectedSet
$$

系统随后构造回归集合：

$$
\mathcal{R}
=
\mathcal{W}_{original}
\cup
\mathcal{W}_{boundary}
\cup
\mathcal{H}_{affected}
$$

其中，$\mathcal{W}_{original}$ 表示生成当前 Governance Contract 的原始 Conflict Witness，用于证明原关系失效已经消失；$\mathcal{W}_{boundary}$ 表示 Governance Predicate 和 Relationship Boundary 附近的验证样本，用于避免治理规则过度收缩或扩展；$\mathcal{H}_{affected}$ 表示受影响 Agent 或 Workflow 的历史成功执行数据，用于验证治理是否破坏已有正常能力。

治理首先必须满足：

$$
Resolved(
\mathcal{W}_{original}
)=1
$$

同时满足：

$$
Regression(
\mathcal{H}_{affected}
)
\leq
\epsilon
$$

并且：

$$
NewHighRiskConflict=0
$$

只有全部条件满足时：

$$
State(GC)
\rightarrow
Active
$$

如果验证失败，系统执行：

$$
Rollback
$$

并将新的失败 Execution Trace 转换为：

$$
W_{new}
$$

重新进入 Detect 阶段。

因此 Verify 并非简单“修复后再测一次”，而是同时验证：

- 原 Conflict 是否消失；
- 治理边界是否正确；
- 受影响历史能力是否保持；
- 是否产生新的高风险关系失效。

## 四、开发者端—用户端协同演进机制

上述第三章描述的是一次完整治理过程。

双端协同的进一步技术价值在于：

> **开发者端和用户端产生的治理状态并非彼此独立，而能够通过 Runtime Evidence 和 Contract Dependency 实现跨端持续演进。**

用户端在真实运行过程中持续形成：

$$
\mathcal{W}_{runtime}
=
\{
W_1,
W_2,
\ldots,
W_n
\}
$$

这些 Witness 最初分别属于不同的 Local Scope。

系统按照 Skill Pair 或 Skill Set、Relationship Violation Type、Root Cause、Context 和 Governance Decision 对其进行聚类，得到：

$$
Cluster_k
$$

对于某一 Cluster，系统计算问题重复频率：

$$
Freq_k=
|Cluster_k|
$$

计算覆盖范围：

$$
Coverage_k
=
\frac{
AffectedUser_k
}{
ActiveUser
}
$$

并计算多个独立用户局部治理结果的一致性：

$$
Consistency_k
=
\frac{
SameResolution_k
}{
|Cluster_k|
}
$$

当某类 Local Relationship Violation 重复出现，并且不同用户形成高度一致的 Governance Decision 时，系统可以判断：

> 该问题可能已经不再是单一用户的特殊 Context 问题，而是共享 Skill Relationship 本身存在普遍缺陷。

当满足：

$$
Freq_k\geq\tau_f
$$

并且：

$$
Consistency_k\geq\tau_c
$$

系统形成：

$$
GCC_k
=
GlobalGovernanceCandidate
$$

提交至开发者端。

开发者可以根据这些 Runtime Evidence 修改共享 Skill，或者形成新的：

$$
GC_G^{(v+1)}
$$

因此完成：

$$
\boxed{
UserRuntimeEvidence
\rightarrow
DeveloperGlobalGovernance
}
$$

另一方面，当开发者端 Global Contract 从：

$$
GC_G^{(v)}
$$

更新为：

$$
GC_G^{(v+1)}
$$

时，与旧 Global Contract 存在依赖关系的 Local Contract 自动满足：

$$
\Delta ParentContract\neq0
$$

因此相关 Local Contract 从：

$$
Active
$$

转换为：

$$
Stale
$$

系统依据第三章定义的 Contract Lifecycle 自动进行：

$$
Stale
\rightarrow
Revalidating
$$

如果新的 Global Contract 已经完全覆盖 Local Contract 所解决的问题：

$$
GC_L^i
\subseteq
GC_G^{(v+1)}
$$

则：

$$
Revalidating
\rightarrow
Retired
$$

如果 Local Contract 仍然包含用户特有的权限、任务或者资源条件，则重新验证通过后：

$$
Revalidating
\rightarrow
Active
$$

继续作为 Local Refinement 存在。

因此双端之间形成完整的状态反馈：

$$
\boxed{
UserRuntimeEvidence
\rightarrow
DeveloperGlobalEvolution
\rightarrow
UserLocalRevalidation
}
$$

开发者端治理共享 Skill 的普遍关系，用户端治理实际使用中的上下文关系；用户端产生的真实运行证据反向修正开发者端的 Global Governance，而新的 Global Governance 又通过 Contract Dependency 和 Lifecycle 重新约束用户端 Local Governance。

这构成本发明“双端协同治理”的核心技术含义。

---

## 五、核心场景矩阵

| 场景 | 主要 Relationship Violation | 主要触发端 | 主要治理约束 |
|---|---|---|---|
| Skill 更新后与已有企业搜索 Skill 能力边界重叠 | Capability / Routing | 开发者端 | Predicate + Priority |
| 用户组合 Web Search 与专业财报 Search | Routing / Specialization | 用户端 | Local Priority + Fallback |
| OCR 与 PDF Analyzer 在扫描文件场景下组合失败 | Precondition / Order | 用户端 | Order |
| 两个操作型 Skills 修改同一运行资源 | Resource / State | 开发者端或用户端 | Exclusion + Isolation |
| Skill 新版本改变 Runtime Dependency | Dependency | 开发者端 | Version Constraint + Isolation |
| 用户不具备某 Skill 所需权限 | Permission | 用户端 | Permission Guard + Fallback |
| 上游 Skill 输出不满足下游输入 | I/O Contract | 用户端 | Adapter + Order |
| 多个用户持续出现相同 Local Violation | Cross-end Evolution | 用户端 → 开发者端 | Global Governance Candidate |
| Global Contract 更新使 Local Contract 失效 | Contract Dependency | 开发者端 → 用户端 | Stale + Revalidation |

## 六、实施例

### 实施例一：开发者端全局能力边界治理

共享 Skill Library 中存在企业内部知识搜索 Skill $S_A$ 和公开 Web 搜索 Skill $S_B^{(v)}$。

开发者将 $S_B$ 修改为：

$$
S_B^{(v+1)}
$$

系统检测：

$$
\Delta D_B\neq0
$$

以及：

$$
\Delta T_B\neq0
$$

说明 Skill 能力语义和 Trigger 均发生变化，因此触发开发者端治理。

系统根据 Skill Contract 建立：

$$
\mathcal{N}(S_B)
$$

并发现 $S_A$ 属于候选相关 Skill。

随后系统抽取二者 Relationship Difference：

$$
\Delta R_{AB}
$$

主要差异来源于：

$$
\Delta_{cap}
$$

和：

$$
\Delta_{trigger}
$$

因此生成 Routing Boundary Violation Hypothesis。

系统据此构造位于能力边界附近的 Query 和数据可见性 Context，并分别执行 $S_A$、$S_B$ 以及同时加载两者的多轮 Agent Simulation。

若：

$$
ViolationRate(W)\geq\tau_v
$$

且观察到相同 Query 在不同运行中分别路由至 $S_A$ 和 $S_B$，并访问不同数据源，则确认：

$$
RV_{AB}
=
RoutingBoundaryViolation
$$

系统根据 Relationship-to-Constraint Mapping 得到：

$$
RI
=
Predicate
+
Priority
$$

由于该关系将影响共享 Skill Library 中多个已有 Agent，治理升级评分满足：

$$
E_s\geq\tau_e
$$

系统触发 Developer Decision。

开发者确定内部未公开信息与公开信息的正确能力边界。

该 Decision 被编译为：

$$
GC_G
$$

其中：

$$
ConstraintClass=Default
$$

并包含 Global Scope、Predicate、Priority、Version 和 Evidence。

Contract 生成后处于：

$$
Candidate
$$

通过 Impact Regression 后：

$$
Candidate
\rightarrow
Verified
\rightarrow
Active
$$

最终：

$$
S_B^{(v+1)}
+
GC_G
$$

正式进入共享 Skill Library。

### 实施例二：用户端局部组合治理

设用户 Agent $A_u$ 已加载两个经过开发者端发布验证的 Skills：

$$
S_C
$$

和：

$$
S_D
$$

当前用户输入的资源状态使：

$$
Precondition(S_D)=False
$$

而：

$$
Postcondition(S_C)
\Rightarrow
Precondition(S_D)=True
$$

系统由此形成：

$$
VH_{CD}
=
OrderingViolationHypothesis
$$

并生成针对当前用户 Context 的 Conflict Witness。

动态执行结果显示：

$$
S_D\rightarrow Fail
$$

而：

$$
S_C
\rightarrow
S_D
\rightarrow
Pass
$$

因此确认：

$$
RV_{CD}
=
OrderingViolation
$$

根据 Relationship-to-Constraint Mapping：

$$
OrderingViolation
\rightarrow
Order
$$

由于该关系明确、风险较低且只影响当前 Agent：

$$
E_s<\tau_e
$$

系统自动生成：

$$
GC_L
$$

其作用域为：

$$
Scope=Agent(A_u)
$$

且：

$$
ConstraintClass=LocalRefinement
$$

包含：

$$
S_C\prec S_D
$$

系统进一步将：

$$
GC_G
$$

与：

$$
GC_L
$$

按照 Constraint Class、Scope 和 Predicate 进行合并。

如果 Global Contract 中不存在不可覆盖的相反 Invariant，则 Local Ordering 在当前 Agent 中生效。

经过局部回归验证后：

$$
GC_L
:
Candidate
\rightarrow
Verified
\rightarrow
Active
$$

该规则只改变当前用户 Agent 的 Planner 行为，不修改共享 Skill Library。

### 实施例三：用户端高风险资源治理

设用户 Agent 同时加载：

$$
S_E
$$

和：

$$
S_F
$$

两个 Skills 均可能修改同一关键运行资源：

$$
R(S_E)\cap R(S_F)\neq\varnothing
$$

系统生成 Resource Violation Hypothesis，并通过动态执行确认两个 Skills 连续运行可能造成不可逆状态变化。

因此：

$$
RV_{EF}
=
ResourceStateViolation
$$

对应治理动作空间为：

$$
Exclusion
+
Isolation
+
RuntimeGuard
$$

由于运行风险高：

$$
E_s\geq\tau_e
$$

系统触发 User Decision。

最终用户确认的治理规则被编译为：

$$
GC_L
$$

对于禁止同时执行的部分形成：

$$
S_E\perp S_F\mid X
$$

如果该资源规则属于不可被局部进一步放宽的安全约束，则其 Constraint Class 可以被设置为更严格的 Local Invariant。

系统在隔离环境中完成验证后使其进入 Active 状态。

当对应资源模型、权限模型或者 Skill Version 后续发生变化时：

$$
\Delta Dependency(GC_L)\neq0
$$

该 Contract 自动进入：

$$
Active
\rightarrow
Stale
\rightarrow
Revalidating
$$

从而避免旧规则在新的资源环境中无限期继续生效。

### 实施例四：用户端 Runtime Evidence 反哺开发者端

多个用户在真实运行过程中分别形成：

$$
W_1,
W_2,
\ldots,
W_n
$$

系统发现这些 Witness 均涉及相同 Skill Pair、相同 Relationship Violation 类型以及相似 Root Cause。

系统计算：

$$
Freq_k\geq\tau_f
$$

且：

$$
Consistency_k\geq\tau_c
$$

说明多个独立用户形成了高度一致的 Local Governance Decision。

系统据此生成：

$$
GCC_k
=
GlobalGovernanceCandidate
$$

并提交至开发者端。

开发者确认后生成新的：

$$
GC_G^{(v+1)}
$$

原有 Local Contract 由于 Parent Contract 或 Skill Version 变化自动进入：

$$
Active
\rightarrow
Stale
$$

系统随后执行：

$$
Stale
\rightarrow
Revalidating
$$

对于已经被新的 Global Contract 完全覆盖的 Local Contract：

$$
GC_L^i
\subseteq
GC_G^{(v+1)}

执行：

$$
Retire(GC_L^i)

对于仍然包含用户特有 Context 的 Local Contract，重新验证成功后恢复：

\rightarrow

$$

至此完成：

$$
\boxed{

\rightarrow
Developer
\rightarrow

}
$$

一次完整双端协同治理循环。

## 七、核心保护点

本发明建议重点围绕以下相互依赖的技术关系进行保护。

第一，开发者端和用户端基于不同 Skill 技术事件触发不同作用域的治理过程。开发者端由 Skill 创建、修改和发布等 Skill 本体变化触发；用户端由 Skill Set、Context、Permission、Resource 或 Runtime 状态变化触发。

第二，对 Candidate Skill Relationship 先提取 Capability、Trigger、Precondition、Resource、State、Dependency、Permission 和 I/O 等差异维度，再形成 Relationship Violation Hypothesis，并据此生成具有上下文、执行策略和观测条件的 Conflict Witness，通过多轮仿真完成动态确认。

第三，将 Confirmed Relationship Violation 映射至受限制的 Resolution Intent，再根据风险和不确定性选择 Automatic Decision、Developer Decision 或 User Decision，从而避免治理结果完全依赖自由生成式模型。

第四，将 Governance Decision 编译为具有 Scope、Predicate、Priority、Exclusion、Order、Fallback、Isolation、Adapter、Version 和 Constraint Class 等属性的机器 Governance Contract，使治理结果直接参与 Skill Retrieval、Routing、Planning 和 Runtime。

第五，通过 Invariant、Global Default 和 Local Refinement 三类约束以及 Scope Specificity 构建 Global Contract 与 Local Contract 的确定性合并规则，并在不可确定合并时重新触发治理。

第六，为 Governance Contract 建立 Candidate、Verified、Active、Stale、Revalidating、Retired 和 RolledBack 生命周期，并根据 Skill Version、Parent Contract、Context Schema、Resource Constraint 和 Permission Model 的变化自动触发 Contract 失效和重新验证。

第七，通过 Runtime Witness 聚合形成 Global Governance Candidate，并在 Global Contract 更新后利用 Contract Dependency 自动使相关 Local Contract 进入 Stale、Revalidating、Retired 或 Active 状态。

上述技术关系共同构成：

> **开发者端—用户端双端协同治理的完整机器状态演化机制。**

## 八、本发明有益效果

本发明通过 Skill Contract 差异分析和候选关系筛选减少进入完整 Agent Simulation 的 Skill 组合数量，降低大规模 Skill Library 的动态治理计算范围。

通过 Violation Hypothesis 和 Conflict Witness，将抽象语义冲突、路由竞争、资源冲突及组合执行异常转换为可重复执行、可观察和可验证的运行证据。

通过 Relationship-to-Constraint Mapping，使不同类型的关系失效能够确定地映射为 Predicate、Priority、Exclusion、Order、Fallback、Isolation、Adapter 等运行约束，降低治理结果的不确定性。

通过 Governance Contract Compiler，将治理判断真正转换为可以直接影响 Skill Retrieval、Routing、Planning 和 Runtime 的机器状态。

通过 Global Contract、Local Contract、Constraint Class 和 Scope Specificity 的确定性合并机制，使用户端能够针对自己的真实运行环境进行局部治理，同时无法突破开发者端已经确认的不可放宽全局约束。

通过 Contract Lifecycle 与 Version Dependency，使治理规则能够随 Skill、Context 和 Global Governance 持续演化，避免过期 Contract 长期参与运行。

通过 Impact Graph 和增量 Regression Set，仅重新验证真正受治理变化影响的 Agent、Workflow 和历史执行数据，降低无差别全量回归开销。

通过 Runtime Evidence 向开发者端反馈以及 Global Contract 向用户端重新传播，使 Skill 治理由一次性冲突处理转变为跨开发者端与用户端持续演进的关系治理过程。

## 十、发明总结

本发明并非一种单纯的 Skill 冲突检测方法，也不是一种简单利用大模型自动修复 Skill 的方法。

其技术本质是建立一种**开发者端—用户端双端协同的 Skill Relationship 治理机制**。

开发者端围绕：

> **Skill 如何安全进入并持续演化于共享生态**

执行全局关系治理。

用户端围绕：

> **已经发布的 Skills 如何在真实用户上下文中正确组合和运行**

执行局部关系治理。

两端共同通过：

$$
\boxed{
\text{Detect}
\rightarrow
\text{Decide}
\rightarrow
\text{Resolve}
\rightarrow
\text{Verify}
}
$$

完成单次治理。

其中 Detect 不仅识别 Candidate Conflict，还通过 Relationship Difference、Violation Hypothesis、Conflict Witness 和 Multi-run Simulation 将关系失效证据化；Decide 将 Relationship Violation 映射至确定的 Resolution Intent，并根据风险选择自动、开发者或用户治理；Resolve 将治理决策编译为可直接控制 Agent Runtime 的 Governance Contract，并通过 Global / Local 确定性合并形成最终机器行为；Verify 则通过 Contract Lifecycle、Impact Analysis 和 Regression Validation 保证治理结果持续有效。

双端之间进一步通过：

$$
\boxed{
\text{User Runtime Evidence}
\rightarrow
\text{Developer Global Evolution}
\rightarrow
\text{User Local Revalidation}
}
$$

形成持续演进。

由此，本发明实现对 Skill 从开发、发布、组合到真实运行全过程中的关系状态进行持续识别、决策、治理、验证和演进，使共享 Skill 生态在不断变化过程中保持稳定的能力边界、调用关系和组合执行关系。
